# ADR-003: REST API и HTTP-контракт

- Статус: `Accepted`
- Дата: 2026-09-03

## Контекст

Продукту требуется API для браузерного fullstack-клиента, автоматизированных тестов и возможных будущих интеграций. В MVP используются обычные ресурсные и командные операции, а публичная система плагинов и сложные внешние интеграции не входят в scope.

API должен иметь единый формат ошибок, поддерживать optimistic locking, быть документирован OpenAPI и не раскрывать данные других рабочих пространств.

## Решение

Backend предоставляет JSON REST API поверх HTTPS.

Основные правила:

- базовый префикс — `/api/v1`;
- ресурсы именуются существительными во множественном числе;
- стандартные HTTP-методы сохраняют свою семантику;
- endpoint не отражает внутреннее расположение Go-пакетов;
- OpenAPI 3.1 является машиночитаемым контрактом API;
- cookie-аутентификация и CSRF-защита определены ADR-004.

Примеры маршрутов:

```text
POST   /api/v1/users
POST   /api/v1/sessions
DELETE /api/v1/sessions/current
POST   /api/v1/workspaces
POST   /api/v1/workspaces/{workspace_id}/invitations
POST   /api/v1/invitations/accept
POST   /api/v1/workspaces/{workspace_id}/projects
POST   /api/v1/projects/{project_id}/issues
POST   /api/v1/issues/{issue_id}/transitions
```

Командный endpoint `/transitions` выбран для смены статуса, потому что операция проверяет workflow и создаёт отдельное событие истории, а не является произвольным PATCH поля.

## HTTP-семантика

| Ситуация | Статус |
|---|---:|
| Ресурс создан | `201 Created` и `Location` |
| Успех без тела | `204 No Content` |
| Невалидные данные | `422 Unprocessable Content` |
| Нет действующей сессии | `401 Unauthorized` |
| Пользователь известен, но роль недостаточна | `403 Forbidden` |
| Ресурс отсутствует или должен быть скрыт tenant-политикой | `404 Not Found` |
| Конфликт бизнес-состояния | `409 Conflict` |
| Отсутствует обязательный `If-Match` | `428 Precondition Required` |
| Версия ресурса устарела | `412 Precondition Failed` |
| Превышен rate limit | `429 Too Many Requests` |

## Формат ошибок

Ошибки возвращаются как `application/problem+json` по RFC 9457:

```json
{
  "type": "https://example.invalid/problems/invalid-status-transition",
  "title": "Invalid status transition",
  "status": 409,
  "code": "INVALID_STATUS_TRANSITION",
  "detail": "The requested transition is not allowed.",
  "request_id": "01...",
  "errors": []
}
```

Production-ответ не содержит stack trace, SQL, имена таблиц, пути файлов и секреты. `code` стабилен для клиента; человекочитаемый `detail` может локализоваться.

RFC 9457 заменяет устаревший RFC 7807: <https://www.rfc-editor.org/info/rfc9457/>.

## Конкурентное обновление

- Версионируемый ресурс возвращает `ETag`, сформированный из его версии.
- Изменяющий запрос передаёт `If-Match`.
- Отсутствие заголовка даёт `428`.
- Несовпадение версии даёт `412` и текущий ETag, если его раскрытие разрешено.
- Проверка версии повторяется в условном SQL-обновлении.

## Идемпотентность и retry

- `GET`, `PUT` и `DELETE` соблюдают HTTP-семантику идемпотентности.
- Для retry-чувствительных `POST` может использоваться `Idempotency-Key` с областью пользователя, endpoint и ограниченным сроком хранения результата.
- Один ключ с другим телом отклоняется конфликтом.
- Идемпотентность HTTP-запроса не заменяет уникальные ограничения и идемпотентность outbox consumer.

Поддержка `Idempotency-Key` обязательна перед нагрузочным тестом для операций, которые автоматически повторяет клиент или reverse proxy.

## Списки, поиск и фильтрация

- Для потенциально больших коллекций используется cursor pagination.
- Сервер устанавливает максимальный размер страницы; значение MVP — 100 элементов.
- Сортировка детерминирована и содержит уникальный tie-breaker.
- Фильтры задаются allowlist-параметрами OpenAPI.
- Поиск не позволяет передать фрагмент SQL, имя колонки или произвольное выражение сортировки.
- Ответ содержит `next_cursor`, но не обязан вычислять дорогой полный `total`.

## Версионирование

- Breaking changes выпускаются под новым major-префиксом.
- Добавление необязательного поля считается обратно совместимым.
- Удаление/переименование поля, изменение его смысла или ужесточение ранее допустимого enum требует новой версии или миграционного периода.
- Устаревшие endpoint имеют срок отключения и наблюдаемую метрику использования.

## Безопасность API

- Каждая операция доступа к ресурсу проверяет object-level и function-level authorization.
- Клиентские поля разбираются строгими DTO; доменные и служебные поля не bind-ятся автоматически.
- CORS использует точный allowlist origin и credentials только для доверенного frontend.
- Изменяющие запросы требуют CSRF-защиту.
- Размер тела, время чтения/записи и количество элементов коллекции ограничены.
- Все SQL-запросы параметризованы.
- HTTPS обязателен вне локальной разработки.

Риски API сверяются с OWASP API Security Top 10 2023: <https://owasp.org/API-Security/editions/2023/en/0x11-t10/>.

## Наблюдаемость

- Каждый запрос получает `request_id`; входящий корректный идентификатор принимается только по доверенной политике.
- Распределённая трассировка использует стандартный `traceparent`.
- Логи содержат метод, шаблон маршрута, статус, длительность и безопасный actor/resource context.
- Метрики используют шаблон маршрута, а не фактический URL с ID, чтобы не создавать высокую cardinality.
- Пароли, cookies, токены, CSRF-значения и полные тела запросов не логируются.

## Последствия

Положительные:

- контракт понятен браузеру, тестам и будущим клиентам;
- стандартная HTTP-семантика уменьшает количество собственных протокольных решений;
- OpenAPI позволяет валидировать совместимость и генерировать клиентские типы;
- ETag/If-Match выражает уже существующую доменную версию задачи.

Отрицательные:

- некоторые бизнес-команды требуют специальных подресурсов;
- cookie-auth требует отдельной CSRF-защиты;
- строгая обратная совместимость требует дисциплины при изменениях;
- cursor pagination сложнее простой схемы offset/limit.

## Рассмотренные альтернативы

- GraphQL — отложен: MVP не требует клиенту произвольной формы выборки, а контроль стоимости запросов усложнил бы защиту.
- gRPC для браузера — отклонён как основной внешний контракт; может использоваться только после появления межсервисной границы.
- Неявный API без OpenAPI — отклонён, поскольку противоречит критериям успеха проекта.

## Критерии пересмотра

- подтверждённая потребность нескольких клиентов в сложных выборках;
- появление публичных интеграций с другими требованиями совместимости;
- необходимость потокового или real-time протокола для конкретного сценария.
