# ADR-002: PostgreSQL как основное хранилище

- Статус: `Accepted`
- Дата: 2026-09-03

## Контекст

Доменная модель содержит связанные данные и строгие инварианты: уникальные membership, ровно один проект для задачи, не более одного активного спринта, атомарное выделение номера задачи, optimistic locking, одноразовые приглашения и неизменяемая история. Для этих операций необходимы транзакции, ограничения целостности и предсказуемая конкурентная модель.

Целевая нагрузка — до 1500 RPS. Она должна подтверждаться тестами и не является основанием заранее добавлять несколько типов хранилищ.

## Решение

PostgreSQL используется как единственный источник истины для транзакционных данных MVP:

- пользователей и сессий;
- рабочих пространств, membership и приглашений;
- проектов, спринтов и задач;
- наблюдателей, комментариев и `IssueEvent`;
- уведомлений;
- transactional outbox.

Реляционные сущности хранятся в нормализованных таблицах. `JSONB` допускается для ограниченного безопасного payload событий и уведомлений, но не заменяет типизированные колонки для полей, по которым выполняются авторизация, связи, сортировка и фильтрация.

## Обязательные механизмы целостности

- `UNIQUE (normalized_email)` для пользователя;
- `UNIQUE (user_id, workspace_id)` для membership;
- уникальность одного действующего приглашения на пару workspace/email;
- `UNIQUE (workspace_id, project_key)`;
- `UNIQUE (project_id, issue_number)`;
- `UNIQUE (issue_id, user_id)` для наблюдателей;
- частичный уникальный индекс для одного `ACTIVE`-спринта на проект;
- внешние ключи для обязательных отношений;
- `NOT NULL` и `CHECK` для фиксированных состояний и локальных ограничений;
- условное обновление `Issue` по `id + version` для защиты от потерянного обновления.

Межтабличные правила, которые невозможно надёжно выразить одним constraint, проверяются application use case внутри транзакции с необходимой блокировкой. Пример — запрет удаления или понижения последнего владельца.

## Транзакции и конкуренция

- Уровень изоляции по умолчанию — `READ COMMITTED`.
- `SELECT ... FOR UPDATE`, условный `UPDATE` или более строгий уровень используются точечно для доказанного инварианта.
- Номер задачи выделяется атомарным обновлением счётчика проекта с `RETURNING`.
- Принятие приглашения блокирует приглашение и защищается уникальностью membership.
- Конфликты сериализации и deadlock допускают ограниченный retry только для явно идемпотентной application-операции.
- Внешние сетевые вызовы не выполняются внутри транзакции PostgreSQL.

## Tenant isolation

Основной контроль доступа выполняется приложением:

1. ресурс загружается вместе с его `workspace_id`;
2. проверяется активное membership текущего пользователя;
3. проверяется требуемая роль;
4. запрос ограничивается тем же workspace.

Составные внешние ключи и ограничения применяются там, где они могут запретить cross-workspace ссылки на уровне данных. PostgreSQL Row-Level Security может быть добавлен позднее как дополнительный слой защиты, но не заменяет application authorization и требует отдельного ADR.

## Миграции

- Любое изменение схемы выполняется версионируемой миграцией из репозитория.
- Применённая миграция не изменяется; исправление выпускается новой миграцией.
- Миграции проверяются на пустой и реалистично заполненной базе.
- Изменения для production проектируются совместимыми с rolling deployment: expand, deploy, backfill, contract.
- Долгие индексы и backfill выполняются контролируемо и наблюдаемо.

## Доступ из Go

- SQL остаётся явным и проверяемым; генерация типизированного кода из SQL допускается.
- Все пользовательские значения передаются параметрами.
- Пул соединений имеет конечные лимиты и метрики ожидания/использования.
- Каждая операция получает `context.Context` с deadline.
- Запросы анализируются через `EXPLAIN (ANALYZE, BUFFERS)` на репрезентативных данных.

Выбор конкретной библиотеки миграций и SQL-доступа фиксируется в техническом ADR после короткого spike, поскольку не меняет доменную модель.

## Outbox и фоновые задания

Business state, `IssueEvent` и outbox-сообщение создаются одной транзакцией. Worker забирает outbox-записи конкурентно безопасно, например небольшими партиями с блокировкой и пропуском уже захваченных строк. Повторная доставка допускается, поэтому обработчики и создание уведомлений идемпотентны.

`IssueEvent` — пользовательская история задачи. Outbox — техническая очередь доставки. Эти сущности имеют разные сроки жизни и ответственность.

## Резервное копирование и восстановление

- Настраиваются автоматические backup и point-in-time recovery, если платформа это поддерживает.
- Процедура восстановления документируется и регулярно проверяется в отдельном окружении.
- Успех backup-задачи не считается доказательством восстановления без restore test.
- Цели RPO/RTO определены в нефункциональных требованиях.

## Последствия

Положительные:

- ACID-транзакции соответствуют границам согласованности;
- ограничения базы являются последней линией защиты от гонок и ошибок приложения;
- один источник истины упрощает эксплуатацию MVP;
- PostgreSQL покрывает обычный поиск и фильтрацию до появления доказанной потребности в отдельном движке.

Отрицательные:

- база может стать узким местом при неправильных запросах и пулах;
- общая схема требует дисциплины владения таблицами между модулями;
- горизонтальное масштабирование записи сложнее масштабирования stateless API;
- outbox требует очистки, мониторинга lag и идемпотентных consumers.

## Рассмотренные альтернативы

- MongoDB — отклонена из-за связанных данных и транзакционных инвариантов.
- Отдельный Elasticsearch с первого релиза — отложен до измерения качества и стоимости поиска PostgreSQL.
- Redis как основное хранилище сессий — отложен; PostgreSQL обеспечивает отзыв и общую доступность при меньшем числе компонентов.
- База на каждый модуль — отклонена для текущего модульного монолита.

## Критерии пересмотра

- подтверждённый нагрузочными тестами предел primary PostgreSQL;
- поисковые требования, которые нельзя выполнить индексами PostgreSQL;
- необходимость отдельного срока хранения или уровня доступности конкретного набора данных;
- требование географически распределённой записи.
