# UC-002: Login

Статус: `Draft v0.1`

## Цель

Проверить учётные данные активного пользователя и создать отзываемую серверную сессию.

## Актор

Неавторизованный пользователь или пользователь, открывающий дополнительную сессию на другом устройстве.

## Предусловия

- Учётная запись ранее создана.
- Запрос выполняется по HTTPS в production-среде.

## Входные данные

| Поле | Обязательность | Правило |
|---|:---:|---|
| `email` | да | Нормализуется той же функцией, что при регистрации |
| `password` | да | Принимается без преобразования и обрезки, в установленном пределе размера |

## Результат

- Создана новая `Session`, принадлежащая пользователю.
- Браузеру установлена новая защищённая session cookie.
- Возвращено безопасное представление пользователя.

## Основной сценарий

1. Система валидирует размер и формат запроса.
2. Нормализует email.
3. Проверяет rate limit для IP, учётного идентификатора и глобального потока входов.
4. Загружает пользователя по нормализованному email.
5. Проверяет пароль, не раскрывая различие между отсутствующим пользователем и неправильным паролем.
6. Проверяет, что пользователь активен и не заблокирован.
7. При необходимости обновляет устаревшие параметры хеша пароля после успешной проверки.
8. Генерирует новый session token и CSRF-секрет.
9. Создаёт серверную сессию и после commit устанавливает cookie.

## Альтернативные сценарии и ошибки

| Условие | Результат |
|---|---|
| Email или пароль не совпадает | `401 INVALID_CREDENTIALS` с единым сообщением |
| Пользователь заблокирован | Внешне тот же `401 INVALID_CREDENTIALS`; причина доступна только security-аудиту |
| Превышен rate limit | `429 RATE_LIMITED` с `Retry-After` |
| Невалидный запрос | `422 VALIDATION_FAILED` |
| Ошибка хранилища | `500 INTERNAL_ERROR`, сессия не создаётся |

## Бизнес-инварианты

- Заблокированный пользователь не может создавать новые сессии.
- Каждая сессия принадлежит ровно одному пользователю.
- Исходный session token не хранится в базе.
- Неуспешный вход не создаёт сессию.
- Пользователь может иметь несколько активных сессий.

## Авторизация

Не требуется. Наличие существующей cookie не даёт возможности обойти проверку новых учётных данных.

## Граница транзакции

Создание `Session` и возможное обновление параметров password hash выполняются атомарно после успешной аутентификации.

## События и аудит

- Успешные и неуспешные попытки входа создают security-события с временем, результатом и минимальными техническими метаданными.
- Пароль, session token и CSRF token в события не попадают.
- Клиентский IP хранится и выводится с учётом принятой политики приватности и доверенных reverse proxy.

## Требования безопасности

- Время и тело ответа не должны очевидно различать отсутствующий email, неверный пароль и блокировку.
- Дорогая проверка пароля защищена rate limit и ограничением параллелизма.
- Новая сессия получает новый случайный идентификатор; идентификатор от клиента не принимается.
- Cookie соответствует ADR-004.
- После изменения уровня привилегий идентификатор сессии обновляется.

## Критерии приёмки

1. Корректные данные активного пользователя создают новую сессию.
2. Неверный email и неверный пароль дают одинаковый внешний ответ.
3. Заблокированный пользователь не получает сессию.
4. Повторные ошибки активируют rate limit.
5. Исходный токен отсутствует в базе и логах.
6. Две сессии одного пользователя могут быть отозваны независимо.
7. Сессия доступна любому экземпляру backend через общее хранилище, а не память процесса.

## Тесты

- Unit: нормализация email и политика rate-limit key.
- Integration: успешная и неуспешная проверка пароля, блокировка, создание сессии.
- Security: user enumeration, credential stuffing, фиксация сессии, cookie-флаги.
- E2E: вход, обновление страницы и доступ к защищённому ресурсу.
