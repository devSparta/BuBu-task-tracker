# UC-008: TransitionIssue

Статус: `Draft v0.1`

## Цель

Изменить статус задачи только по разрешённому workflow, защитить обновление от потери изменений и записать полную историю перехода.

## Актор

Активный участник рабочего пространства задачи с ролью `OWNER`, `ADMIN` или `MEMBER`.

## Предусловия

- Задача и её проект существуют и не архивированы.
- У пользователя есть активное membership в workspace проекта.
- Клиент ранее получил текущую версию задачи.
- Сессия действительна, CSRF-проверка пройдена.

## Входные данные

| Поле | Обязательность | Правило |
|---|:---:|---|
| `issue_id` | да | Идентификатор задачи из маршрута |
| `target_status` | да | Одно из `TODO`, `IN_PROGRESS`, `REVIEW`, `DONE` |
| `expected_version` | да | Текущая известная клиенту положительная версия; передаётся через `If-Match` |

## Разрешённые переходы

| Из | В | Назначение |
|---|---|---|
| `TODO` | `IN_PROGRESS` | Начало работы |
| `IN_PROGRESS` | `TODO` | Возврат к планированию |
| `IN_PROGRESS` | `REVIEW` | Передача на проверку |
| `REVIEW` | `IN_PROGRESS` | Возврат на доработку |
| `REVIEW` | `DONE` | Завершение работы |
| `DONE` | `TODO` | Повторное открытие задачи |

Все остальные переходы запрещены, включая `TODO → DONE` и `IN_PROGRESS → DONE`.

## Результат

- Статус задачи изменён.
- Версия задачи увеличена ровно на `1`.
- Создан `IssueEvent`; для `DONE → TODO` используется семантика повторного открытия.
- Создано outbox-сообщение для уведомлений.
- Возвращены новое состояние и новый ETag.

## Основной сценарий

1. Система аутентифицирует пользователя и проверяет CSRF.
2. Загружает задачу, проект и workspace в разрешённом контексте.
3. Проверяет активное membership и роль.
4. Проверяет, что задача и проект не архивированы.
5. Сравнивает `expected_version` с текущей версией.
6. Проверяет наличие пары «текущий статус → целевой статус» в фиксированном workflow.
7. В одной транзакции условно обновляет статус и увеличивает версию.
8. Создаёт `IssueEvent` со старым и новым статусом, инициатором и временем.
9. Создаёт outbox-сообщение.
10. После commit возвращает задачу с новой версией.

## Альтернативные сценарии и ошибки

| Условие | Результат |
|---|---|
| Задача отсутствует или недоступна текущему пользователю | `404 ISSUE_NOT_FOUND` |
| Роль `VIEWER` | `403 INSUFFICIENT_ROLE` |
| Задача или проект архивированы | `409 ISSUE_READ_ONLY` |
| `expected_version` отсутствует | `428 PRECONDITION_REQUIRED` |
| Версия устарела | `412 ISSUE_VERSION_MISMATCH` и текущий ETag |
| Переход отсутствует в workflow | `409 INVALID_STATUS_TRANSITION` |
| Целевой статус равен текущему | `409 STATUS_UNCHANGED` |
| Ошибка записи истории или outbox | Полный откат изменения статуса |

## Бизнес-инварианты

- Статус изменяется только по разрешённым переходам.
- Каждое изменение статуса создаёт неизменяемый `IssueEvent` в той же транзакции.
- `DONE → TODO` считается повторным открытием и явно отражается в истории.
- Обновление принимается только для ожидаемой версии.
- Архивированная задача доступна только для чтения.
- Роль проверяется в workspace конкретной задачи.

## Авторизация

| Роль | Разрешение |
|---|:---:|
| `OWNER` | да |
| `ADMIN` | да |
| `MEMBER` | да |
| `VIEWER` | нет |

Workflow одинаков для всех разрешённых ролей MVP. Ограничение переходов только исполнителем в текущую модель не входит.

## Граница транзакции

Одна транзакция PostgreSQL:

1. условное обновление `Issue` по `id + expected_version`;
2. увеличение `version`;
3. вставка `IssueEvent`;
4. вставка outbox-сообщения.

Создание и доставка `Notification` выполняются асинхронно после commit.

## События и уведомления

- Обычный переход создаёт событие `ISSUE_STATUS_CHANGED`.
- Переход `DONE → TODO` создаёт событие `ISSUE_REOPENED`.
- История содержит только безопасный снимок `status: before/after` и необходимые метаданные.
- Worker уведомляет постановщика, исполнителя и наблюдателей по правилам notification-модуля; инициатор по умолчанию исключается из получателей.
- Уникальный ключ события и получателя предотвращает дубликаты при повторной обработке.

## Требования безопасности

- `issue_id` не является доказательством доступа; membership проверяется на каждом запросе.
- Для недоступного объекта возвращается `404`, чтобы не подтверждать его существование.
- Статус и версия разбираются строго, неизвестные значения отклоняются.
- История не содержит session token, CSRF token, cookie или лишние персональные данные.
- События изменения статуса входят в аудит чувствительных действий.

## Критерии приёмки

1. Каждый переход из таблицы выполняется для разрешённой роли.
2. Каждый отсутствующий в таблице переход отклоняется без изменения данных.
3. `TODO → DONE` и `IN_PROGRESS → DONE` запрещены.
4. `DONE → TODO` создаёт событие повторного открытия.
5. Два клиента с одной версией не могут перезаписать друг друга: успешен не более чем один.
6. Ошибка истории или outbox откатывает изменение задачи.
7. `VIEWER` и пользователь другого workspace не изменяют статус.
8. Retry обработки outbox не создаёт дубликаты уведомлений.

## Тесты

- Unit: табличный тест всех 16 комбинаций статусов.
- Integration: optimistic locking, транзакция задачи/истории/outbox, параллельное обновление.
- Authorization: матрица ролей и cross-workspace негативные случаи.
- Security: CSRF, подмена ID, mass assignment, отсутствие секретов в истории.
- E2E: переходы на Kanban-доске, конфликт двух вкладок и повторное открытие.
