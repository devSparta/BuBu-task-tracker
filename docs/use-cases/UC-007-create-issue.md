# UC-007: CreateIssue

Статус: `Draft v0.1`

## Цель

Создать задачу внутри проекта, атомарно выделить её человекочитаемый номер и записать начальное событие истории.

## Актор

Активный участник рабочего пространства проекта с ролью `OWNER`, `ADMIN` или `MEMBER`.

## Предусловия

- Проект существует и не архивирован.
- У инициатора есть активное membership в workspace проекта.
- Сессия действительна, CSRF-проверка пройдена.

## Входные данные

| Поле | Обязательность | Правило |
|---|:---:|---|
| `project_id` | да | Идентификатор проекта из маршрута |
| `title` | да | После trim от 1 до 240 символов |
| `description` | нет | Markdown, не более 100 000 символов |
| `priority` | да | `LOW`, `MEDIUM`, `HIGH` или `CRITICAL` |
| `assignee_user_id` | нет | Активный участник того же workspace |
| `sprint_id` | нет | Спринт того же проекта, не `COMPLETED` |
| `deadline` | нет | Время с часовым поясом; может находиться в прошлом |

Статус, постановщик, порядковый номер и версия не принимаются от клиента.

## Результат

- Создана неархивированная `Issue` со статусом `TODO` и версией `1`.
- Постановщиком назначен текущий пользователь.
- Выделен неизменяемый номер внутри проекта и сформирован ключ, например `CORE-42`.
- Создан неизменяемый `IssueEvent` типа `ISSUE_CREATED`.
- Создано outbox-сообщение для асинхронной обработки уведомлений.

## Основной сценарий

1. Система аутентифицирует пользователя и проверяет CSRF.
2. Загружает проект вместе с workspace только в разрешённом контексте.
3. Проверяет роль `OWNER`, `ADMIN` или `MEMBER` и отсутствие архивации проекта.
4. Валидирует заголовок, Markdown, приоритет и дедлайн.
5. Если назначен исполнитель, проверяет его активное membership в workspace проекта.
6. Если назначен спринт, проверяет принадлежность проекту и состояние, отличное от `COMPLETED`.
7. В транзакции атомарно получает и увеличивает следующий номер задачи проекта.
8. Создаёт задачу со статусом `TODO`, постановщиком-инициатором и версией `1`.
9. Создаёт `IssueEvent` с безопасным снимком начальных полей.
10. Создаёт outbox-сообщение, ссылающееся на бизнес-операцию и событие истории.
11. После commit возвращает задачу и её версию/ETag.

## Альтернативные сценарии и ошибки

| Условие | Результат |
|---|---|
| Проект отсутствует, недоступен или относится к другому workspace | `404 PROJECT_NOT_FOUND` |
| Роль `VIEWER` | `403 INSUFFICIENT_ROLE` |
| Проект архивирован | `409 PROJECT_ARCHIVED` |
| Исполнитель не является активным участником workspace | `422 ASSIGNEE_NOT_WORKSPACE_MEMBER` |
| Спринт принадлежит другому проекту | `422 SPRINT_PROJECT_MISMATCH` |
| Спринт завершён | `409 SPRINT_COMPLETED` |
| Некорректные поля | `422 VALIDATION_FAILED` |
| Конфликт или ошибка выделения номера | Транзакция откатывается, номер не используется задачей частично |

## Бизнес-инварианты

- Пара «проект + номер» уникальна и неизменяема.
- Постановщик является активным участником workspace проекта.
- Исполнитель, если задан, является активным участником того же workspace.
- Спринт, если задан, принадлежит тому же проекту.
- Отсутствие спринта означает backlog и не изменяет статус `TODO`.
- Дедлайн в прошлом допустим и означает просроченную задачу.
- Архивированный проект не принимает новые задачи.
- Задача не удаляется физически через пользовательские сценарии.

## Авторизация

| Роль | Разрешение |
|---|:---:|
| `OWNER` | да |
| `ADMIN` | да |
| `MEMBER` | да |
| `VIEWER` | нет |

## Граница транзакции

Одна транзакция PostgreSQL:

1. атомарное выделение следующего номера проекта;
2. вставка `Issue`;
3. вставка `IssueEvent`;
4. вставка outbox-сообщения.

Уведомления создаются асинхронно после commit и не входят в эту транзакцию.

## События и уведомления

- `IssueEvent` — источник истории для пользователя и не редактируется.
- Outbox-сообщение — технический механизм гарантированной передачи факта изменения worker-процессу.
- Worker определяет получателей по актуальным правилам. При назначенном исполнителе он может создать ему внутреннее уведомление.
- Повторная обработка outbox-сообщения не создаёт дубликаты уведомлений благодаря ключу идемпотентности.

## Требования безопасности

- Markdown хранится как исходный текст, а при отображении проходит безопасный render/sanitize pipeline.
- Произвольные HTML, JavaScript URL и опасные атрибуты не должны исполняться.
- Идентификаторы исполнителя и спринта проверяются через проект/workspace, а не только по факту существования.
- Сервер игнорирует клиентские попытки задать reporter, status, version, issue number или archived state.
- Параметризованные SQL-запросы обязательны.

## Критерии приёмки

1. Разрешённая роль создаёт задачу со статусом `TODO`, версией `1` и текущим пользователем как reporter.
2. Две параллельные операции получают разные последовательные номера без дубликатов.
3. Ошибка `IssueEvent` или outbox откатывает создание задачи и выделение номера.
4. Задача без `sprint_id` находится в backlog.
5. Спринт другого проекта и пользователь другого workspace отклоняются.
6. `VIEWER` не может создать задачу.
7. Клиент не может подменить постановщика или начальный статус.
8. Созданная задача возвращает версию, пригодную для `If-Match`.

## Тесты

- Unit: валидация полей и правила assignee/sprint.
- Integration: транзакция, конкурентное выделение номера, история и outbox.
- Authorization: все роли и cross-workspace ссылки.
- Security: stored XSS через Markdown, mass assignment, SQL injection payloads.
- E2E: создание задачи из UI и появление её в backlog/спринте.
