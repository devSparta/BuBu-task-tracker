# UC-004: InviteMember

Статус: `Draft v0.1`

## Цель

Создать одноразовое ограниченное по времени приглашение пользователя в рабочее пространство с заранее определённой ролью.

## Актор

Активный участник рабочего пространства с ролью `OWNER` или `ADMIN`.

## Предусловия

- Рабочее пространство существует.
- У инициатора есть активное членство в этом рабочем пространстве.
- Сессия действительна, CSRF-проверка пройдена.

## Входные данные

| Поле | Обязательность | Правило |
|---|:---:|---|
| `workspace_id` | да | Берётся из маршрута и проверяется в контексте текущего пользователя |
| `email` | да | Нормализуется общей функцией identity-модуля |
| `role` | да | Только `ADMIN`, `MEMBER` или `VIEWER` |

Срок действия задаётся серверной политикой. Значение MVP: 72 часа; изменение срока не должно требовать изменения доменной модели.

## Результат

- Создано приглашение в состоянии `PENDING`.
- В базе сохранён только хеш одноразового токена.
- Инициатору возвращена одноразовая ссылка с исходным токеном, доступная только в ответе создания.

До выбора канала автоматической доставки MVP предполагает, что инициатор безопасно передаёт ссылку получателю самостоятельно. Email-доставка потребует отдельного use case и обновления threat model.

## Основной сценарий

1. Система аутентифицирует инициатора и проверяет CSRF.
2. Загружает workspace в разрешённом для пользователя контексте.
3. Проверяет активное членство и роль `OWNER` или `ADMIN`.
4. Нормализует email и проверяет назначаемую роль.
5. Проверяет, что получатель ещё не является активным участником workspace.
6. Проверяет отсутствие действующего `PENDING`-приглашения для пары «workspace + email».
7. Генерирует криптографически случайный одноразовый токен и вычисляет его хеш.
8. Создаёт `WorkspaceInvitation` с автором, сроком действия и состоянием `PENDING`.
9. После commit возвращает инициатору одноразовую ссылку; исходный токен не журналируется и не может быть запрошен повторно.

## Альтернативные сценарии и ошибки

| Условие | Результат |
|---|---|
| Workspace не существует или недоступен пользователю | `404 WORKSPACE_NOT_FOUND` |
| Роль инициатора `MEMBER` или `VIEWER` | `403 INSUFFICIENT_ROLE` |
| Запрошена роль `OWNER` | `422 OWNER_INVITATION_FORBIDDEN` |
| Email уже принадлежит активному участнику | `409 USER_ALREADY_MEMBER` |
| Действующее приглашение уже существует | `409 INVITATION_ALREADY_PENDING` |
| Невалидный email или роль | `422 VALIDATION_FAILED` |
| Превышен лимит приглашений | `429 RATE_LIMITED` |

Повторная отправка и перевыпуск токена оформляются отдельным сценарием; они не создаются скрыто этим use case.

## Бизнес-инварианты

- Приглашение принадлежит ровно одному workspace и имеет одного автора.
- Автор является активным `OWNER` или `ADMIN` этого workspace.
- Приглашение не назначает роль `OWNER`.
- Исходный токен не хранится.
- Для пары «workspace + нормализованный email» существует не более одного действующего `PENDING`-приглашения.

## Авторизация

| Роль | Разрешение |
|---|:---:|
| `OWNER` | да |
| `ADMIN` | да |
| `MEMBER` | нет |
| `VIEWER` | нет |

Проверка выполняется по workspace из маршрута; роль из другого workspace не учитывается.

## Граница транзакции

Транзакция создаёт `WorkspaceInvitation`. Исходный токен существует только в памяти обрабатывающего процесса до формирования ответа и не входит в persisted state.

Если ответ потерян, существующее приглашение не раскрывает токен повторно. Инициатор должен отозвать его и создать новое через отдельный сценарий перевыпуска.

## События и аудит

- Аудит содержит автора, workspace, роль, время и результат без исходного токена.
- `IssueEvent` не создаётся.

## Требования безопасности

- Токен содержит не менее 256 бит энтропии и сравнивается по хешу.
- Токен не передаётся в query-параметры сторонних ресурсов и не попадает в access-логи.
- Endpoint защищён CSRF и rate limit по пользователю и workspace.
- Ответ не раскрывает наличие аккаунта с указанным email за пределами сведений, необходимых инициатору workspace.
- Поля автора, состояния и срока действия устанавливаются сервером.

## Критерии приёмки

1. `OWNER` и `ADMIN` могут пригласить пользователя на разрешённую роль.
2. `MEMBER` и `VIEWER` получают отказ.
3. Через приглашение нельзя назначить `OWNER`.
4. В базе отсутствует исходный токен.
5. Параллельные запросы не создают два действующих приглашения для одной пары workspace/email.
6. Повторное чтение приглашения не раскрывает исходный токен или ссылку.
7. Приглашение из workspace A не предоставляет никаких прав в workspace B.

## Тесты

- Unit: допустимые роли, нормализация email, расчёт срока.
- Integration: уникальность активного приглашения и хранение только token hash.
- Authorization: вся матрица ролей и cross-workspace негативные проверки.
- Security: утечка токена через логи, rate limit, CSRF.
- E2E: владелец создаёт приглашение, копирует показанную один раз ссылку и передаёт её получателю.
