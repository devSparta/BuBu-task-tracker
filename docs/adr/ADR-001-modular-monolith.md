# ADR-001: Модульный монолит

- Статус: `Accepted`
- Дата: 2026-09-03

## Контекст

Продукт включает пользователей и сессии, рабочие пространства и роли, проекты, спринты, задачи, комментарии, историю и уведомления. Между этими областями существуют строгие транзакционные инварианты:

- workspace создаётся вместе с первым владельцем;
- приглашение принимается вместе с созданием membership;
- задача создаётся вместе с номером и событием истории;
- изменение задачи фиксируется вместе с `IssueEvent`;
- завершение спринта изменяет сразу несколько задач.

Целевая нагрузка составляет до 1500 RPS, при этом backend должен горизонтально масштабироваться и не хранить пользовательское состояние в памяти экземпляра. Проект разрабатывается как сильный учебный fullstack-кейс, поэтому архитектура должна демонстрировать границы модулей, тестируемость и эксплуатационные практики без преждевременной распределённости.

## Решение

Система реализуется как модульный монолит на Go с одной кодовой базой и одной основной базой PostgreSQL.

Логические модули соответствуют доменной модели:

| Модуль | Ответственность |
|---|---|
| `identity` | Пользователи, пароли, сессии и аутентификация |
| `workspace` | Workspace, membership, роли и приглашения |
| `project` | Проекты, ключи и счётчики задач |
| `sprint` | Состояния спринтов и планирование задач |
| `issue` | Задачи, workflow, комментарии, наблюдатели и `IssueEvent` |
| `notification` | Формирование, хранение и чтение уведомлений |

Каждый модуль делится на следующие уровни ответственности:

- `domain` — сущности, value objects и чистые бизнес-правила;
- `application` — use cases, авторизация на уровне сценария и управление транзакцией;
- `ports` — минимальные интерфейсы, необходимые application-слою;
- `adapters` — HTTP, PostgreSQL, фоновые обработчики и внешняя доставка.

Допускается структура вида:

```text
cmd/
├── api/
└── worker/
internal/
├── identity/
├── workspace/
├── project/
├── sprint/
├── issue/
├── notification/
└── platform/
```

`cmd/api` и `cmd/worker` собираются из одной кодовой базы и используют те же модули. Выделение worker в отдельный процесс является эксплуатационным решением, а не микросервисной границей.

## Правила зависимостей

1. Domain-код не зависит от HTTP, SQL-драйвера, логгера или конкретного фреймворка.
2. HTTP-обработчик не содержит бизнес-правил и вызывает один application use case.
3. Application-слой задаёт границу транзакции.
4. Модуль не изменяет таблицы другого модуля напрямую из обработчика; межмодульная операция выполняется через явно определённый application API/port.
5. Общий пакет `platform` содержит только технические примитивы: транзакции, часы, генератор ID, логирование, метрики и конфигурацию. Он не становится хранилищем общей бизнес-логики.
6. Циклические зависимости модулей запрещены и проверяются структурой пакетов.
7. Асинхронные реакции используют transactional outbox. Outbox не заменяет доменную историю `IssueEvent`.

## Развёртывание и масштабирование

- API не хранит сессии, rate-limit state или задания только в памяти экземпляра.
- Несколько реплик API работают с общим PostgreSQL и общими инфраструктурными хранилищами.
- Фоновые задания допускают несколько worker-реплик с конкурентным безопасным захватом задач.
- Сначала API и worker могут запускаться одним развёртыванием; раздельное масштабирование допускается без изменения границ доменных модулей.

## Последствия

Положительные:

- транзакционные инварианты реализуются без распределённых транзакций;
- локальная разработка и отладка остаются воспроизводимыми;
- модульные границы видимы в коде и тестах;
- систему можно горизонтально масштабировать репликами;
- проект демонстрирует архитектурную дисциплину без операционной стоимости микросервисов.

Отрицательные:

- ошибка границ пакетов может превратить систему в связанный монолит;
- все модули используют общий цикл релиза;
- база данных остаётся общим узким местом и требует измерений, индексов и контроля соединений;
- раздельное масштабирование отдельных доменных модулей невозможно без их выделения.

## Рассмотренные альтернативы

### Микросервисы с первого релиза

Отклонено: добавляют сетевые отказы, распределённую согласованность, discovery, отдельные деплои и сложную наблюдаемость, не решая подтверждённую проблему текущего масштаба.

### Монолит, разделённый только на `handlers/services/repositories`

Отклонено: технические слои не защищают границы `identity`, `workspace`, `issue` и других частей предметной области.

### Serverless-функция на каждый endpoint

Отклонено: усложняет транзакционные сценарии, локальную воспроизводимость и контроль соединений PostgreSQL.

## Критерии пересмотра

Решение пересматривается, если измерения покажут хотя бы одно из условий:

- модулю требуется независимый жизненный цикл релиза;
- отдельный модуль невозможно масштабировать в составе общего процесса экономически приемлемо;
- граница данных и согласованности стала асинхронной по бизнес-смыслу;
- требования изоляции или отказоустойчивости нельзя выполнить в текущем процессе.

Выделение сервиса требует отдельного ADR и плана миграции данных.
