# Проектная документация task tracker

Статус комплекта: `Draft v0.1`  
Дата: 2026-09-03

## Назначение

Комплект переводит продуктовые требования и доменную модель в проверяемые сценарии приложения и архитектурные решения. Он предназначен для начала реализации модульного монолита на Go с PostgreSQL и REST API.

Источники требований:

- `product-brief.md` — продукт, границы MVP и целевые характеристики;
- `domain-model.md` — сущности, роли, связи, переходы и бизнес-инварианты.

Перед добавлением комплекта в репозиторий исходные файлы следует назвать именно `product-brief.md` и `domain-model.md` и положить в этот же каталог `docs/`.

## Как читать комплект

1. Product brief определяет, что входит в продукт.
2. Domain model определяет сущности и правила, которые нельзя нарушать.
3. Use case описывает один законченный результат для пользователя и границу транзакции.
4. ADR объясняет выбранное техническое решение и его последствия.
5. Нефункциональные требования задают измеримые критерии качества.
6. Модель угроз связывает риски с защитными мерами и проверками.

## Правила изменений

- Изменение продуктового поведения сначала вносится в product brief или use case.
- Изменение сущностей, ролей, переходов или инвариантов сначала вносится в domain model.
- Существенное техническое решение оформляется новым ADR; принятый ADR не переписывается задним числом, а заменяется следующим ADR.
- Изменение API отражается в OpenAPI и тестах контракта.
- Изменение меры безопасности отражается в threat model и негативных тестах.

## Уточнения, добавленные этим комплектом

Product brief и domain model не задают некоторые точные значения, необходимые для проверяемых сценариев. В документах предложены следующие значения MVP; их следует подтвердить перед реализацией соответствующего среза:

| Решение | Предложенное значение |
|---|---|
| Поведение после регистрации | Автоматически создать первую сессию |
| Срок приглашения | 72 часа |
| Повторное активное приглашение | Не создавать второе для той же пары workspace/email |
| Доставка приглашения | Показать ссылку инициатору один раз; автоматическую доставку спроектировать отдельно |
| Ключ проекта | 2–10 символов `A–Z0–9`, первый символ — буква |
| Session timeout | 12 часов бездействия, не более 30 дней абсолютно |
| RPO/RTO | 15 минут / 60 минут (`Proposed`) |
| Лимиты пользовательских полей | Зафиксированы в use cases и NFR для защиты ресурсов |

Эти уточнения не меняют существующие сущности, роли, workflow или матрицу прав. Если значение не подходит продукту, меняется соответствующий use case/ADR до написания кода.

## Что ещё не является частью этого комплекта

- физическая схема PostgreSQL и миграции;
- OpenAPI-спецификация;
- UI-макеты;
- сценарии управления спринтами, архивирования, комментариев, наблюдателей и уведомлений;
- инструкция по эксплуатации и восстановлению;
- план и отчёт нагрузочного тестирования.

Эти документы создаются по мере реализации соответствующих вертикальных срезов.
