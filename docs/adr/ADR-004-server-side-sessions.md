# ADR-004: Серверные пользовательские сессии

- Статус: `Accepted`
- Дата: 2026-09-03

## Контекст

MVP требует регистрацию, вход, выход, несколько пользовательских сессий, отзыв текущей или всех сессий и немедленный запрет новых сессий для заблокированного пользователя. Роли меняются в контексте рабочих пространств, поэтому долгоживущий автономный токен не должен сохранять устаревшие полномочия.

Backend масштабируется горизонтально и не может хранить авторизационное состояние только в памяти одного экземпляра.

## Решение

Используются серверные сессии с непрозрачным случайным bearer token в cookie.

При создании сессии:

1. сервер генерирует CSPRNG-токен с энтропией не менее 256 бит;
2. исходный токен возвращается только браузеру;
3. в PostgreSQL сохраняется криптографический хеш токена и метаданные `Session`;
4. каждый запрос вычисляет хеш предъявленного токена и проверяет сессию, пользователя, сроки и отзыв;
5. полномочия workspace загружаются из актуального membership, а не кодируются в session token.

Для высокоэнтропийного случайного токена применяется быстрый криптографический хеш с безопасным сравнением. Password hashing и session-token hashing — разные задачи: пароль обрабатывается адаптивным Argon2id, session token уже имеет достаточную случайность.

## Cookie

Production-cookie имеет параметры:

```text
__Host-session=<opaque-token>; Secure; HttpOnly; SameSite=Lax; Path=/
```

- Префикс `__Host-` запрещает `Domain`, требует `Secure` и `Path=/`.
- `HttpOnly` запрещает JavaScript читать токен.
- `Secure` разрешает передачу только по HTTPS.
- `SameSite=Lax` выбран, чтобы переход по верхнеуровневой ссылке приглашения с внешней страницы не терял пользовательскую сессию.
- `SameSite` используется как дополнительная защита, а не замена CSRF token.

Рекомендации по cookie соответствуют OWASP Session Management Cheat Sheet: <https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html>.

## Сроки и отзыв

Значения MVP:

- idle timeout — 12 часов;
- absolute timeout — 30 дней;
- сервер проверяет оба срока;
- активность продлевает только idle deadline и никогда не выходит за absolute deadline;
- истёкшие и отозванные записи периодически удаляются фоновым заданием после периода, необходимого для аудита.

Выход отзывает текущую сессию. Смена пароля и блокировка пользователя отзывают все активные сессии одной транзакционной операцией или делают их немедленно недействительными через проверку состояния пользователя.

## CSRF-защита

Для изменяющих состояние методов применяется synchronizer token pattern:

- случайный CSRF token связан с серверной сессией;
- frontend получает его через безопасный same-origin ответ, но не из session cookie;
- клиент отправляет его в заголовке `X-CSRF-Token`;
- сервер сравнивает значение с сессией и дополнительно проверяет `Origin`/Fetch Metadata;
- `GET`, `HEAD` и `OPTIONS` не изменяют состояние;
- CSRF token не попадает в URL и логи.

OWASP рекомендует synchronizer token для stateful-приложений и подчёркивает, что `SameSite` не заменяет токен: <https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html>.

При использовании версии Go со стандартной защитой cross-origin requests она может применяться как дополнительный слой после отдельной проверки применимости и тестов.

## Обновление идентификатора

Новая сессия создаётся:

- после успешной регистрации;
- после каждого успешного входа;
- после повышения привилегий или другого чувствительного изменения, если текущая сессия сохраняется.

Сервер не принимает идентификатор сессии, предложенный клиентом, и не переиспользует предыдущий токен.

## Хранение

`Session` содержит как минимум:

- `id`;
- `user_id`;
- `token_hash` с уникальным индексом;
- `csrf_secret` или его защищённое представление;
- `created_at`, `last_seen_at`, `expires_at`, `absolute_expires_at`;
- `revoked_at` и причину отзыва;
- минимальные метаданные устройства, если они действительно используются интерфейсом управления сессиями.

Исходные токены, полные User-Agent без необходимости и лишние персональные данные не сохраняются.

## Авторизация и tenant isolation

Сессия подтверждает личность, но не право на ресурс. Каждый workspace-запрос отдельно проверяет:

1. активность пользователя;
2. активное membership в workspace ресурса;
3. требуемую роль;
4. дополнительные бизнес-инварианты.

Изменение или удаление membership начинает действовать без ожидания истечения session token.

## Масштабирование

- Сессии доступны всем API-репликам через PostgreSQL.
- Локальный кеш не является источником истины и не может продлевать жизнь отозванной сессии.
- Индекс по `token_hash` и ограниченный пул соединений обязательны.
- Добавление распределённого кеша допускается только после измерений и должно сохранять корректный отзыв.

## Последствия

Положительные:

- немедленный отзыв и управление несколькими устройствами;
- токен не содержит персональных данных и ролей;
- изменение membership действует сразу;
- компрометация базы не раскрывает готовые bearer tokens;
- горизонтальные API-реплики используют единое состояние.

Отрицательные:

- каждый защищённый запрос требует серверной проверки;
- cookie-auth требует CSRF-защиты;
- PostgreSQL получает дополнительную read-нагрузку;
- нужно очищать истёкшие сессии и отслеживать аномалии.

## Рассмотренные альтернативы

### Долгоживущий JWT access token

Отклонён для MVP: усложняет немедленный отзыв, изменение ролей и блокировку пользователя; список отзыва фактически возвращает серверное состояние.

### Токен в `localStorage`

Отклонён: JavaScript получает прямой доступ к bearer token, что увеличивает последствия XSS.

### Сессии только в памяти API

Отклонены: нарушают горизонтальное масштабирование и теряются при рестарте.

### Redis с первого релиза

Отложен до измерений: добавляет отдельный stateful-компонент, пока PostgreSQL покрывает функциональные и нагрузочные требования.

## Критерии приёмки решения

- исходный token отсутствует в базе и логах;
- отозванная или истёкшая сессия отклоняется любой API-репликой;
- cookie имеет ожидаемые флаги;
- изменяющий запрос без корректного CSRF token отклоняется;
- изменение membership немедленно меняет авторизацию;
- нагрузочный тест включает проверку session lookup.

## Критерии пересмотра

- session lookup становится подтверждённым bottleneck;
- появляется отдельный публичный API для небраузерных клиентов;
- появляется федеративная аутентификация/OIDC;
- требования мобильного приложения входят в scope.
