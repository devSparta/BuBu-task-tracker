# UC-001: RegisterUser

Статус: `Draft v0.1`

## Цель

Создать глобальную учётную запись пользователя и сразу открыть серверную сессию, чтобы пользователь мог продолжить основной сценарий и создать рабочее пространство.

## Актор

Неавторизованный пользователь.

## Предусловия

- Запрос выполнен по HTTPS в production-среде.
- Клиент ещё не обязан иметь сессию.

## Входные данные

| Поле | Обязательность | Правило |
|---|:---:|---|
| `email` | да | Корректный email, после нормализации не более 254 символов |
| `password` | да | От 12 до 128 символов; не обрезается и поддерживает Unicode |
| `display_name` | да | После удаления внешних пробелов от 1 до 100 символов |

Точная функция нормализации email должна быть единой для регистрации, входа и приглашений. Нормализованное значение используется для сравнения и уникальности.

## Результат

- Создан активный `User`.
- Создана активная `Session`.
- Браузеру установлена защищённая session cookie.
- Возвращено безопасное представление пользователя без хеша пароля и данных сессии.

## Основной сценарий

1. Система проверяет формат и размер запроса.
2. Нормализует email и отображаемое имя.
3. Проверяет пароль по принятой политике.
4. Проверяет отсутствие пользователя с тем же нормализованным email.
5. Вычисляет адаптивный хеш пароля с уникальной солью.
6. Генерирует криптографически случайный session token и CSRF-секрет.
7. В одной транзакции создаёт пользователя и серверную сессию, сохраняя только хеш session token.
8. После успешного commit устанавливает session cookie и возвращает созданного пользователя.

## Альтернативные сценарии и ошибки

| Условие | Результат |
|---|---|
| Некорректные или слишком большие данные | `422 VALIDATION_FAILED` |
| Email уже зарегистрирован | `409 EMAIL_ALREADY_REGISTERED` |
| Ограничение частоты запросов превышено | `429 RATE_LIMITED` |
| Конфликт уникальности из-за параллельной регистрации | `409 EMAIL_ALREADY_REGISTERED` |
| Ошибка хранилища или генератора случайных данных | Откат транзакции и безопасный `500 INTERNAL_ERROR` |

Ответы об ошибках не содержат SQL, stack trace, хешей, внутренних идентификаторов инфраструктуры или переданного пароля.

## Бизнес-инварианты

- Нормализованный email уникален в системе.
- Пароль и session token никогда не сохраняются и не журналируются в открытом виде.
- Сессия принадлежит ровно одному пользователю.
- Частично созданное состояние «пользователь без ожидаемой первой сессии» не появляется в результате этого сценария.

## Авторизация

Не требуется. На endpoint действуют отдельные ограничения частоты по IP и нормализованному идентификатору, не раскрывающие состояние других пользователей.

## Граница транзакции

Одна транзакция PostgreSQL:

1. вставка `User`;
2. вставка `Session`.

Cookie устанавливается только после успешного commit. Ошибка отправки ответа не отменяет commit; повторная регистрация безопасно остановится на уникальности email.

## События и аудит

- `IssueEvent` не создаётся: он относится только к истории задач.
- Факт успешной и отклонённой регистрации записывается как структурированное security-событие без пароля, session token и полного набора персональных данных.

## Требования безопасности

- Для пароля используется Argon2id с параметрами не ниже принятого проектом минимума; параметры хранятся вместе с хешем и могут повышаться.
- Сравнение хеша выполняется безопасной библиотечной реализацией.
- Session token генерируется CSPRNG и содержит не менее 256 бит энтропии.
- В базе хранится только хеш session token.
- Cookie соответствует ADR-004.
- В логах email маскируется или заменяется стабильным внутренним идентификатором там, где полное значение не требуется.

## Критерии приёмки

1. Валидные данные создают пользователя и рабочую сессию.
2. Повторная регистрация с эквивалентным нормализованным email не создаёт дубликат.
3. Два параллельных запроса с одним email создают не более одного пользователя.
4. В базе и логах отсутствуют исходный пароль и исходный session token.
5. Ошибка создания сессии откатывает создание пользователя.
6. Cookie содержит `Secure`, `HttpOnly`, `SameSite` и корректные `Path`/`Max-Age` согласно ADR-004.
7. Невалидные и слишком большие запросы отклоняются до дорогостоящего хеширования пароля.

## Тесты

- Unit: нормализация email, политика пароля, валидация имени.
- Integration: транзакция пользователя и сессии, уникальность email, параллельная регистрация.
- Security: отсутствие секретов в логах, rate limit, безопасные cookie-флаги.
- E2E: регистрация в браузере и доступ к защищённому endpoint с созданной сессией.
